# 事故复盘（postmortem） 0005：并发进程重复写入了会话日志中已提交的序号

[English](0005-concurrent-process-writers-duplicated-committed-sequences.md) | 中文

Status: resolved（JSONL 后端已加入追加时范围守护；跨进程存活信号仍待建设）

## 摘要

两个共用同一 `~/.dsh` 主目录的 `dsh web` 服务加载了同一个会话，并向其日志各自追加事件。其中一个持有正在等待长时间 `pwsh` 调用的活动轮次；另一个在已存储前缀中发现了一个未闭合的轮次，合成崩溃恢复的收尾事件，并用活动轮次即将使用的序号提交了它们。工具返回后，活动轮次在同样的四个序号上追加了真实结果，因此已提交区域中这四个序号各出现两次，读取方随即拒绝了整个产物：该会话无法再被恢复，其后续 11,078 个真实事件在所有产品读取路径上都无法抵达。进程内的所有权跟踪、准备阶段的修订版本检查，以及只回滚自身部分写入的追加路径，共同导致没有任何代码能观察到另一个写入方，也没有任何测试让两个进程作用于同一个会话。持久的教训是：任何写入方追加之前，会话产物都需要一个位于日志之外的存活或所有权信号；在该信号存在之前，两个入口作用于同一会话会静默地损坏它。

## 概述

JSONL 后端每次提交追加一个逻辑批次，每个批次都是一个独立的带校验和 Zstandard 帧；所有读取方都会拼接帧、要求 `seq` 连续，并拒绝已提交区域中的不连续（`dsh-session-persistence-jsonl` 的 `format.ts:362`）。因此崩溃恢复的职责很窄：当已存储前缀以一个未闭合的轮次结尾时，[`interruptedTurnClosers`](../../packages/core/session/src/repair.ts) 会合成缺失的 `tool/result`、`step/end` 与 `turn/end`，其序号从已存储最后一个事件的 `seq + 1` 开始，并由 [`commitPrepared`](../../packages/session/session-persistence/src/coordinator.ts) 经 `commitRepair` 提交。

上述每一项判断都局限在单个进程内。所有权保存在协调器的内存映射中，因此 `commitPrepared` 只会拒绝它看得见的第二个所有者，`isPreparedSourceCurrent` 也只比较准备期间读取到的修订版本。[`appendLines`](../../packages/session/session-persistence-jsonl/src/index.ts) 以追加模式打开日志，只回滚自身批次的部分写入，从不询问自本所有者游标以来是否有别的写入方扩展过该文件。

真正让两个写入方相撞的是恢复期序号的计算方式。恢复从它加载的已存储前缀推导首个 `seq`，而活动写入方的下一个 `seq` 是它内存中的事件计数；对同一前缀而言两者是同一个数字。两个写入方各自都正确，合在一起就把相同的序号写了两遍。

读取方的拒绝是设计行为，而且这个缺口早已被记录：[session.md](../subsystems/session.md) 指出，要容忍并发写入方就需要日志之外的存活信号；[end-seed 边界说明](../../.agents/notes/implemented/architecture/2026-07-30-session-end-seed-log-boundary.md) 重申该边界不是关于其他写入方的存活信号；[可继续 subagent 说明](../../.agents/notes/implemented/feature/2026-07-28-continuable-subagent-conversations.md) 记录了进程内的所有权图不协调两个 harness 进程。由于该失效始终没有实际发生过的实例，这个信号一直没有被实现。

## 影响

受影响的会话（`Install dsh web UI plugins`，`session-fec7b85f-358a-4984-80a6-846800e8091c`）彻底不可用。GUI 报出 `internal: resume failed for session "…": Error: corrupt session log: seq gap in committed region at line 3788 (expected 68382, got 68378)`，来源是 [`agent-lookup.ts`](../../packages/api/remotes/src/agent-lookup.ts)；历史加载以同样的扫描器拒绝告终，用户正在阅读的 transcript 也不再推进。

没有任何事件字节丢失，损坏仅限于四个重复的序号。代价全部体现为可用性：所有读取方都在重复处停下，因此后续 11,078 个完好事件（`seq` 68378–79855）——包括活动轮次正在等待的那个工具结果——都无法从 GUI、CLI 以及任何 SDK 客户端抵达。

其触发条件属于日常桌面使用，而非罕见部署：任何两个共用同一主目录的入口，无论是两个 Web 端口，还是 Web 服务与 CLI 或 ACP 写入方并存，只要打开同一会话就会触发。

## 证据

产物为 `~/.dsh/sessions/--C-selfDIr-Tools-dsh-dsh-zackary--/session-fec7b85f-358a-4984-80a6-846800e8091c/session.jsonl.zstd`：1,219,286 字节、2,244 个 Zstandard 帧、4,397 条记录、最大逻辑 `seq` 为 79,855。按序解码每个帧，得到一段直到 `seq 68381` 的连续前缀，随后是一条从 `seq 68378` 重新开始、并一直连续到结尾的分支。

恢复块在工具调用后 9.0 秒落地，此时工具仍在运行；真实结果则在调用后 37.4 秒到达。帧 1917 承载三条收尾事件，帧 1918 承载 `session/end-seed` 标记，帧 1919 承载真实 `tool/result` 及其 `step/end`；也就是说每个写入方的贡献都是一个完整帧，无需解码即可在帧粒度上看到重叠。

用后端自身的 `SessionLogScanner` 扫描该产物，可精确复现产品错误：`corrupt session log: seq gap in committed region at line 3788 (expected 68382, got 68378)`。该行号是扫描器的事件行计数，不含头部记录；出问题的记录位于第 3789 个物理行。

检查这些产物时，有两个进程正作用于该主目录：`@deepseek-ai/dsh/lib/bin.js web --port 43120`（已安装构建）与 `node --import tsx/esm apps/cli/src/bin.ts web --port 43123`（即报告该故障的窗口所用的源码构建）。仅凭产物无法把某个帧归因到某个 PID，因此这只是观察到的配置组合，不能证明哪个端口写了哪个帧。

同一主目录下还有第二个会话存在同类碰撞，且完全不涉及崩溃恢复。`session-da0c4819-1b86-44b0-a791-4c5494a47578`（cwd 为 `C:\workDir\Download\C++简历`，1,151 帧，最大 `seq` 45,845）把创建事实记录为 `seq` 0–2，129 秒后在 `seq` 3 记录 `session/end-seed`——即第二个进程基于该已存储前缀构造 `Session` 时写入的 seed 边界——随后又在 `seq` 3 记录 `agent/inbox/spliced`，时间比该标记晚 239 秒，来自内存中事件计数仍为 3 的活动会话。两次碰撞相隔 17.8 分钟，本次在前。

## 时间线

- 某个进程上的活动轮次为一条长时间运行的 `pwsh` 命令记录 `tool/call`，并等待其结果。
- 9.0 秒后，第二个进程加载同一会话，发现未闭合的轮次，提交了合成的收尾事件及其 seed 边界，从而使持久化日志越过了活动写入方的游标。
- 调用后 37.4 秒，活动轮次在 `seq 68378` 追加真实 `tool/result`，并把该轮次继续到 `seq 79855`，使用的都是已被占用的序号。
- 之后的某次恢复扫描该产物，在重复处停止保留前缀并拒绝它；GUI 把该拒绝呈现为一次失败的模型操作和一次失败的历史加载。
- 恢复过程丢弃了两个伪造帧，产物随后在后端自身的读取方上扫描通过。

## 根因

所有权是按进程划分的。协调器的 `states` 与 `live` 映射、`already has a live persistence owner` 拒绝，以及已准备来源的修订版本检查，描述的都只是单个进程内的写入方，而没有任何机制能让一个进程发现另一个进程拥有该会话。

恢复期的序号计算假定已存储前缀就是最新状态。`interruptedTurnClosers` 从它加载到的内容推导收尾事件，这只有在没有其他写入方推进该前缀时才成立；而活动写入方的事件计数会独立地达到同一个值。

碰撞并不需要崩溃恢复参与。基于已存储前缀构造 `Session` 的进程同样会在下一个 `seq` 写入该 seed 的 `session/end-seed` 边界，与仍在基于同一前缀计数的活动写入方相撞；第二个受损会话正是仅因该边界而重复。

追加路径无法察觉外部写入方。`appendLines` 只校验自身的写入，而基于过期序号基准追加的批次是格式良好的字节，读取方只能事后拒绝。

没有任何门禁覆盖该配置。所有持久化测试套件都只让每个进程运行一个协调器，因为它们没有可断言的跨进程机制；而引发本次事故的部署形态——同一主目录上运行同一产品的两个实例——既没有警告，也没有锁，更没有文档化的禁止说明。

## 恢复

丢弃帧 1917 与 1918 只移除了伪造事件。每个帧都可独立解码，因此该修复既不需要重新压缩，也不需要重新编号，幸存事件中所有 `sourceEventSeqs` 引用仍然指向它记录时的序号。

重建后的产物通过后端自身的 `SessionLogScanner` 与 Zstandard 帧解码器：2,242 帧、79,856 个事件、序号 0–79855 连续，且已提交前缀等于整个文件，不再有撕裂尾部。它以 `step/start` 结尾，因此下次加载会为该未闭合步骤追加普通的崩溃收尾事件。

原始字节保存在产物旁边，文件名为 `session.jsonl.zstd.corrupt-20260918-115823.bak`。发现逻辑只匹配 `*.jsonl` 与 `*.jsonl.zstd`，因此该备份对 `list()` 和恢复过程都不可见。

第二个产物 `session-da0c4819-…` 也以同样方式修复：丢弃其重复的 seed 边界帧；其原始字节保存为 `session.jsonl.zstd.corrupt-20260918-114024.bak`。其余 45,846 个事件从 `seq` 0 到 45,845 连续，日志以一个已闭合的 `turn/end` 结尾，因此不会再补写收尾事件。对该主目录下全部 52 份会话产物的扫描（共 3,462,225 个事件）报告无拒绝、无撕裂尾部。

这是对两个产物的修复。它并不能防止问题再次发生，防复发由下面的防护措施承担。

## 已添加的防护措施

JSONL 后端现在会拒绝不再延续其写入方所观测范围的持久化变更，并在任何字节改变之前抛出 `SessionPersistenceConflictError`（见 [Agent Note](../../.agents/notes/implemented/bug-fix/2026-09-18-session-artifact-concurrent-writer-refusal.md)）。三个包内测试分别固定了追加拒绝、脱离式读取重新观测到外部产物后的拒绝，以及本会丢弃另一写入方已提交轮次的被拒截断修复；一个无密钥组装场景固定了面向产品的拒绝文本。下面其余选项仍待落实，而刻意跨进程共享同一会话仍需要其中之一。

- **追加时范围守护（已实现）。** 每次完整读取与每次持久写入都会记录产物的字节长度与已提交事件计数，不再延续该范围的追加或截断修复都会以冲突错误拒绝。它限于后端，并把静默损坏变为显式失败；它不会让第二个进程使用该会话，只会阻止其继续破坏。
- **带存活信号的会话占用。** 每个会话一份所有者记录（进程身份外加心跳或启动时间，并在崩溃后接管过期记录），可为所有入口提供真正的跨进程互斥，代价是要自行承担过期判定、接管与拆卸语义。
- **按主目录的实例守护。** 在同一主目录上拒绝第二个会写入会话的入口，以低成本覆盖本次报告的配置，但会阻断合法的多实例使用，且不覆盖 Web、CLI 与 ACP 写入方混用的情况。
- **读取方容忍。** 让保留前缀越过重复区域，会把从未按该顺序发生过的历史当作事实提供；而在该处截断会丢弃 11,078 个真实事件。拒绝是正确的，缺陷在上游。针对重复已提交区域的有意恢复操作属于独立的产品决策，而不是读取方的默认行为。

## 教训

- 一旦某个产物可能有多个写入方，进程内的锁就不再是互斥；只能追加的日志在首次追加之前就需要一个位于自身之外的信号。
- 没有存活信号的确定性恢复是不成立的。从已存储前缀合成收尾事件等于断言该轮次已结束，这对崩溃成立，对仍然持有它的活动写入方不成立。
- 事后修正产物需要一条与读取方无关且有文档记录的路径。扫描器的拒绝保住了真相，却把其后的工作困在原地，因此恢复依赖于了解物理帧布局。
- 既无防护也无警告的配置本身就是缺陷面。同一主目录上的两个入口看起来是被支持的，在产品给出相反提示之前，没有任何东西说明它不是。
